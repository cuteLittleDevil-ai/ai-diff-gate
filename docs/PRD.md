## 1. 背景

当前使用 Nginx 作为 AI 请求网关时，对 SSE 流式响应支持不够友好（存在缓冲问题）。同时，希望参考 pi-agent 一类设计，实现多模型协议适配，并支持「一个请求同时访问多个模型」后进行结果对比。

本项目定位为轻量级 Go Demo，用于验证「统一接入 + 多模型扇出 + 结果对比 + 页面展示」这条链路是否好用，而非替代现有生产网关。

---

## 2. 目标

构建 **ai-diff-gate**，在本地可一键启动的前提下，实现：

1. **统一接口 + 多厂商协议适配**：至少覆盖 OpenAI 与 Anthropic 两家协议形态。
2. **单请求扇出（fan-out）**：一次提交 Prompt，并发调用多个已配置模型。
3. **文本结果对比**：对多份回复做可读的文本 Diff。
4. **HTML 并排展示**：在页面上并排查看各模型输出与差异，便于人工判断。

成功标准见第 8 节「产品级验收标准」。

---

## 3. 非目标

本阶段明确不做、也不承诺：

| 项 | 说明 |
|----|------|
| 生产级网关 | 不含额度、用户体系、复杂运营后台 |
| 高可用与计费 | 不含集群、计费、SLA 承诺 |
| 流式 SSE 作为 P0 | SSE 可后续扩展，本阶段以同步请求为主 |
| 完整安全与合规体系 | Key 由用户自备；Demo 不做密钥托管与审计平台 |

## 5. 用户与场景

### 5.1 目标用户

- 开发者（作者本人，以及后续可能开源后的同类用户）。
- 需要快速对比不同模型对同一 Prompt 响应差异的人。

### 5.2 核心场景（四步）

1. 用户输入一个 Prompt，并选择（或按配置使用）多个模型。
2. 系统并发调用这些模型。
3. 系统收集响应后计算差异（文本为主；延迟、token 等为增强信息）。
4. 用户在 HTML 页面并排查看各模型结果与差异。

模型如何在页面勾选、是否同时提供 JSON API，见开放问题 Q3、Q4。

## 6. 功能需求

### 6.1 MVP（必须 / 优先）

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| F1 | 协议适配 | 支持 OpenAI、Anthropic 至少两家协议适配 | P0 |
| F2 | 多模型扇出 | 一个请求并发调用多个模型 | P0 |
| F3 | 结果对比 | 对返回内容做文本差异对比 | P0 |
| F4 | HTML 展示 | 提供 HTML 页面并排展示各模型结果与差异 | P0 |
| F5 | 配置驱动 | 通过配置文件管理模型与 API Key | P0 |
| F6 | 基础指标 | 记录并展示延迟、token 用量（如有） | P1 |

### 6.2 扩展（非本阶段必交付）

- 更多模型适配：Gemini、DeepSeek、本地模型等。
- SSE 流式输出。
- 语义相似度对比。
- 更完善的前端 UI。
- 请求历史记录。

## 7. 产品级验收标准

以下从产品/干系人视角判断「Demo 是否可用」：

1. 能通过配置接入至少 2 个不同协议的模型。
2. 一次请求能同时获得多个模型的响应。
3. 能在 HTML 页面看到并排结果和基本文本差异。
4. 项目可本地一键启动（例如 `go run` 或预构建二进制）。
5. 结构清晰，后续扩展新模型时不必推翻主流程。

技术契约与用例级细节见 `docs/SPEC.md`；实现方案见 `docs/DESIGN.md`。

## 8. 风险与约束（产品视角）

| 风险 / 约束 | 影响 | 缓解思路（产品层） |
|-------------|------|-------------------|
| 各厂商 API Key 需用户自行配置 | 无法「开箱即用」连真实模型 | 文档说明自备 Key；提供示例配置结构 |
| 不同模型响应格式差异大 | 适配成本高，对比体验可能不一致 | MVP 只保证两家；展示侧统一成可比文本 |
| 第一阶段以同步请求为主 | 长 Prompt / 慢模型时页面等待感强 | 接受 Demo 体验；SSE 列入扩展 |
| Demo 性质 | 不保证生产性能与稳定性 | 明确对外表述为 Demo，不承诺 SLA |

部分失败、超时等语义会影响「对比是否完整」，产品默认策略见开放问题 Q1，技术默认建议见 SPEC。

## 9. 开放问题（产品决策）

下列问题需产品侧拍板；编号与 `DESIGN.md` / `SPEC.md` 对齐。

| 编号 | 问题 | 说明 |
|------|------|------|
| Q1 | 部分模型失败时的语义与超时 | 一模型超时/报错时，是整单失败，还是展示成功子集并标注失败？超时默认多久？ |
| Q2 | Diff 粒度与空白处理 | 按行、按词还是按段？空白差异是否忽略？ |
| Q3 | 交付形态：仅 HTML vs 同时 JSON API | MVP 是否必须同时提供可编程 JSON 接口？ |
| Q4 | 模型选择方式 | 页面勾选，还是配置写死本轮对比集？ |
| Q5 | Key 存放方式 | 明文 YAML、环境变量、`.env`，或组合？ |
| Q6 | 定位：OpenAI 兼容透明代理 vs 对比专用 API | 是否伪装成可替换的 OpenAI 代理，还是只做对比入口？ |
| Q7 | 产品名是否还会改 | 是否继续用 `ai-diff-gate`，或改用备选名之一？ |
